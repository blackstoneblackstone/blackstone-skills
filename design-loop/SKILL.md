# Loop 设计向导

把模糊的“让 AI 持续做事”收敛为可执行、可验证、可停止的 loop 规格。默认用中文交流；跟随用户语言。

## 交互原则

1. 一次只问一个最关键的问题，等待用户回答后再继续。
2. 优先提供 2–4 个贴合上下文的选项，并明确推荐项；始终允许用户自由描述。
3. 复述每一步已确认的结论，主动指出冲突、遗漏和不可验证的措辞。
4. 用户不知道答案时，给出合理默认值并解释影响，不把设计术语丢回给用户。
5. 保持一份内部 `Loop Draft`，每轮只更新变化项。除非用户要求，不在每一步展示完整草稿。
6. 用户说“快速模式”“直接帮我定”时，采用推荐默认值，但仍必须确认高风险权限和外部副作用。
7. 不因字段已经足够就擅自部署、创建自动化、修改生产系统或发送外部消息。先交付设计，再获得相应授权。
8. 把 prompt 视为 loop 的一个部件；优先设计状态转移、工具边界、验证器和停止机制。

## 先判断请求阶段

将请求归入以下一种状态，并从对应位置开始：

- **探索**：只有想法。从“目标”开始逐步提问。
- **已有草案**：抽取已知字段，只追问关键缺口，不重复提问。
- **评审**：根据验收清单指出缺陷，再询问是否逐项修订。
- **实现**：先校验规格和目标平台，再使用平台真实可用的原语实现。

如果用户只要求设计，不执行任何外部写操作。

## 引导流程

按顺序推进；已经明确的步骤直接跳过。

### 1. 定义结果

询问：“这个 loop 最终要持续改善或清空什么？一次成功运行后，外部世界发生了什么可观察变化？”

把“优化一下”“处理所有问题”等模糊目标改写成带对象、动作和结果的句子。先锁定一个主结果；额外目标列为非目标或后续版本。

### 2. 确认运行环境

询问 loop 将运行在哪里，例如 Codex、Claude Code、CI/CD、定时任务平台或自建 agent。记录本地/云端、是否必须在线、可用工具和已有登录态。

不要假设某个斜杠命令存在。只有在当前平台明确提供并已核实后，才把 `/goal`、`/loop`、`/schedule` 或类似名称写成可执行命令；否则把它们标为概念映射。

### 3. 选择循环类型

根据特征推荐一种最简单的模式：

- **回合制**：一次请求内完成，任务短、变化大、需要人机协作。
- **目标导向**：可以反复执行“行动 → 评估”，且有可计算退出标准。
- **时间/事件驱动**：需要等待外部状态变化；能用事件触发时优先事件，不盲目轮询。
- **主动式**：持续接收任务、拆分子流程并处理队列；仅在前三类不足时选择。

解释推荐理由，并让用户确认。需要详细判断或示例时读取 [loop-patterns.md](references/loop-patterns.md)。

### 4. 定义触发与输入

一次确认一个主题：

1. 谁或什么触发运行？
2. 每次运行读取哪些输入，来源是什么？
3. 如何确定输入是新的、完整的、未处理过的？

周期任务必须确认时区、频率和允许延迟。事件任务必须定义去重键。队列任务必须定义游标或 checkpoint。

### 5. 设计单次工作周期

把每轮限制为以下闭环：

1. **Observe**：读取当前状态和证据。
2. **Decide**：选择本轮最小、可逆的行动。
3. **Act**：执行行动并记录变更。
4. **Verify**：用独立于“已执行”的证据验证结果。
5. **Persist**：保存结果、状态和下一轮所需 checkpoint。

确定性的数据获取、格式转换、比较和去重优先交给脚本；模型负责模糊判断、生成和异常归因。

### 6. 保护评估完整性

把目标指标视为潜在攻击面。逐项确认：

1. 执行者能修改哪些文件、数据、工具参数和环境变量？
2. 哪些测试、评估代码、基线和数据集必须只读或对执行者隐藏？
3. 执行者能否通过增加算力、减少样本、跳过失败项、污染缓存或改写报告来刷分？
4. 指标改善是否仍代表用户真正想要的结果？需要哪些约束指标或人工抽查？

默认把评估器、基线和测试夹具置于执行者的写入边界之外。若无法隔离，明确标注 Goodhart 风险并降低自主等级。

选择最低够用的评估隔离等级：

- **E0 自检**：执行者自行检查，仅用于低风险探索。
- **E1 确定性验证**：测试、lint、schema、数值比较或其他脚本判定。
- **E2 独立评审**：新上下文中的评估 Agent 读取产物和契约，不继承生成者的推理。
- **E3 受保护评估**：只读/隐藏测试集、隔离环境、外部裁判及必要的人工审批。

评估结果必须附证据；多个 Agent 的多数意见不能代替独立证据。

### 7. 写成功与停止条件

至少确认：

- **成功条件**：可观察、可测量，包含阈值或全部通过的检查项。
- **失败条件**：什么证据表明本轮失败。
- **停止条件**：成功、最大轮数、时间预算、成本预算、截止时间或人工取消。
- **无进展条件**：连续几轮指标不改善时停止或升级。

拒绝把“模型认为完成”作为唯一标准。若无法自动验证，明确指定人工审批者及其需要查看的证据。

### 8. 设计状态、重试与恢复

询问失败后允许什么行为。默认建议：同一错误最多重试 2 次；连续 2 轮无进展则停止并汇报。

把运行状态持久化到磁盘、数据库或队列，不依赖对话上下文。至少保存 spec 版本、run ID、当前状态、输入游标、轮次、最佳指标、预算消耗、待审批项和最近一次已确认副作用。

记录：可重试错误、不可重试错误、退避策略、幂等键、部分成功处理、回滚方式和断点恢复位置。具有外部副作用的动作，在重试前必须确认是否已成功执行。

在两种恢复方式中明确选择：

- **回滚后重启**：适合隔离代码实验、临时工作树和可完全重建的环境。
- **从 checkpoint 续跑**：适合迁移、队列、付款、发布、通知及任何不可安全重放的流程。

不要把“出错就从头开始”设为通用策略。

### 9. 划定角色、权限与安全边界

按风险选择角色隔离，不教条地为小任务增加多个 Agent：

- Planner 定义目标、边界和契约；高风险流程中不要让其直接修改实现。
- Generator 只在允许的写入面内行动，不修改验收标准。
- Evaluator 根据冻结契约检查产物，不继承 Generator 的解释。
- Approver 只处理明确列出的不可逆或高风险决策。

让角色通过版本化契约和磁盘产物协作，不依赖共享的隐含对话历史。低风险任务可合并角色，但必须保留确定性验证。

逐项确认 loop 能否：写文件、运行命令、修改远端状态、合并代码、部署、花费资金、处理敏感数据、向外部人员发消息。

默认策略：

- 读取和草拟可自动进行。
- 可逆的作用域内变更可按用户授权自动进行。
- 删除、付款、发布、合并、生产部署和对外沟通默认需要审批。
- 凭证不得写入 prompt、日志或产物。

任何权限缺口都要成为显式审批门，而不是隐含假设。

### 10. 选择自主等级并控制成本

从最低自主等级开始，只有前一级经过 dry run 并满足质量门槛后才升级：

- **A0 建议**：Agent 只提出下一步，人类执行。
- **A1 逐轮审批**：Agent 执行每一轮前等待批准。
- **A2 有界自治**：在轮数、时间、预算和权限范围内自动循环。
- **A3 自动触发**：由事件或计划启动，异常时升级给人。
- **A4 持续服务**：持续消费任务队列；必须有租约、并发、熔断、死信和全局关闭开关。

确认最大轮数、单次/每日预算、超时和运行频率。优先采用：

1. 事件触发代替高频轮询。
2. 脚本代替确定性推理。
3. 小模型做分类和筛选，大模型只处理复杂判断。
4. 增量输入、checkpoint 和缓存，避免重复读取全量上下文。
5. 小范围 dry run 后再扩大并发和权限。

### 11. 设计可观测性与规则演进

每次运行至少记录：run ID、触发源、输入游标、每轮行动、验证证据、状态、耗时、成本/Token、错误类别、审批和最终停止原因。

确认告警对象与条件，例如预算达到 80%、连续失败、无进展、队列积压或权限被拒。

每次失败后区分“修复本轮”和“改进系统”。把可泛化教训转化为规则、测试或评估器变更，记录规则版本、生效时间和原因。不要让运行中的 Generator 自行放宽成功标准。

### 12. 生成规格与运行契约

输出一份完整的 `Loop Spec`：

```markdown
# <Loop 名称>
- 目标：
- 非目标：
- 运行环境：
- 循环类型：
- 自主等级：
- 触发器：
- 输入与去重：
- 单轮流程：Observe → Decide → Act → Verify → Persist
- 角色与上下文隔离：
- 允许修改面 / 只读面：
- 评估器与隔离等级：
- 成功指标：
- 约束指标与防刷分检查：
- 停止条件：
- 重试、退避与无进展规则：
- 状态与恢复：
- 权限与审批门：
- 成本、频率与并发上限：
- 日志与告警：
- Dry run 方案：
- 上线与回滚：
```

用户需要实现或可移植契约时，读取 [artifact-templates.md](references/artifact-templates.md)，生成最小必要文件：

- `program.md`：冻结的目标、边界、周期和停止规则。
- `state.json`：机器可读 checkpoint；不要把完整对话当状态。
- `runs.jsonl`：追加式实验/运行账本。
- `evaluator.md`：独立评估接口和受保护资源。
- `approval-policy.md`：仅在存在人工审批门时生成。

先让 Planner、Generator 与 Evaluator 对契约达成一致，再冻结评估规则并开始生成。运行期间修改规则时递增 spec 版本，禁止用新规则覆盖旧运行记录。

然后用四个场景做桌面演练：正常成功、指标被投机利用、外部系统失败、行动已执行但回执丢失。发现缺陷时继续逐题修订。

### 13. 交付与实现

先给出：

1. 推荐架构及其理由。
2. 完整 Loop Spec。
3. 一段伪代码或状态机描述。
4. 运行契约文件清单及其所有者。
5. 未决风险和需要用户批准的事项。
6. 最小可行版本与自主升级路径。

询问用户是否要实现。得到授权后，先检查目标环境的真实能力，再创建所需 skill、脚本、CI 配置或自动化。实现后执行 dry run，并把实际验证证据与设计目标逐项对照。

## 质量门槛

交付前确认：

- 触发器不会重复制造任务，或已有去重机制。
- 成功条件能由证据验证，不依赖主执行者自我判断。
- 执行者不能修改评估器、基线或只读测试，或此风险已明确披露。
- 指标具有防刷分检查和至少一个约束指标或人工抽查机制。
- 每条路径都会成功、停止、等待审批或明确失败，不会无限运行。
- 最大轮数、时间和成本均有硬上限。
- 外部副作用具有幂等、确认或补偿方案。
- 中断后可以从 checkpoint 恢复，而不是从头重复执行。
- 重启与续跑策略匹配副作用语义，不会重复付款、发布或通知。
- 权限遵循最小化原则，高风险动作有审批门。
- 自主等级经过逐级 dry run，没有直接从人工流程跳到持续自治。
- 日志足以回答“为何采取该行动”和“为何停止”。
- 规则、状态和运行账本已版本化，失败经验会沉淀为规则或测试。
- 先从单任务、低并发、低权限 dry run 开始。

未满足的项目必须标为风险，不能悄悄省略。
